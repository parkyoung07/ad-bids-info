# SignBid 운영 정책 및 데이터 승인 체계 (OPERATIONS_POLICY)

## 1. 개요 및 거버넌스 원칙
본 문서는 SignBid 서비스의 공고 데이터 상태 전이, 마감 판정, 승인 권한, 배포 통제 규칙을 정의한다.
SignBid는 입찰 적격성을 자의적으로 판정하는 서비스가 아니며, 공식 조달청 OpenAPI 및 공공 데이터를 가공 없이 전달하는 "경량형 기회 레이더"이다.

---

## 2. 공고 데이터 10대 상태 전이 체계 (Data State Lifecycle)

모든 공고 데이터는 아래 10단계 상태 규격을 따르며, 허가되지 않은 상태 도약(State Jump)은 원천 차단된다.

| 상태 코드 | 한글 명칭 | 설명 및 처리 기준 | 전이 가능 조건 |
| :--- | :--- | :--- | :--- |
| `COLLECTED` | 수집 완료 | 공공 API에서 원문 데이터를 최초 수집한 상태 | 수집 파이프라인 가동 시 |
| `FILTERED` | 필터링 완료 | 옥외광고·인쇄 4대 업종 키워드 및 제외 필터 적용 완료 | 필터링 스크립트 실행 후 |
| `REVIEW_REQUIRED` | 검수 대기 | 충돌 가능성 또는 신규 후보로 사람의 육안 검수가 필요한 상태 | 자동분류 완료 시 |
| `HOLD_MISSING_DEADLINE` | 마감일 결측 보류 | 공식 마감일시(`bidClseDt`)가 원문에 없어 보류된 상태 | 마감일 결측 확인 시 |
| `STAGED` | Staging 반영 | Staging 테스트 서버에 반영되어 검증 가능한 상태 | `npm run deploy:staging` |
| `APPROVED` | 운영 승인 | **회장님께서 운영 배포를 최종 승인한 상태 (AI/개발자 자의 부여 금지)** | **회장님 명시적 승인** |
| `PUBLISHED` | 운영 공개 | 실제 운영 서버(`main` 브랜치)에 배포되어 대외 공개된 상태 | `npm run deploy:production` |
| `CLOSED` | 마감 | 투찰 마감일시(`bidClseDt`)가 현재 시각을 경과한 상태 (KST 시·분·초 기준) | 마감시각 도래 시 |
| `CANCELLED` | 취소 | 발주기관에서 취소공고를 게시한 상태 | 취소공고 연동 시 |
| `DATA_CONFLICT` | 데이터 충돌 | API 원문 간 불일치, 마감일 충돌, URL 파라미터 불일치 등 격리 상태 | 무결성 위반 감지 시 즉시 격리 |
| `REJECTED_OUT_OF_SCOPE` | 부적합 배제 | 순수 전기공사, 교육/연구 등 무관 공고로 판정되어 공개에서 영구 제외된 상태 | 검수 후 영구 배제 |

## 3. 마감시한 운영 원칙 및 상태 판정 5단계 우선순위

1. **마감시한 판정 (KST 시·분·초 정밀 비교):**
   - `isOpen = officialCloseDateTime !== null && currentKstTime < officialCloseDateTime`
   - `isClosed = officialCloseDateTime !== null && currentKstTime >= officialCloseDateTime`
   - 공식 마감시각 전까지는 남은 시간이 짧더라도 진행 공고로 표시하며, 24시간 등 임의의 사전 제외 기준을 두지 않는다.

2. **남은 시간에 따른 마감 임박 배지 표시:**
   - `24시간 초과`: `자동수집 후보`
   - `24시간 이하`: `마감 임박`
   - `3시간 이하`: `긴급 · 마감 임박`
   - `1시간 이하`: `긴급 · 1시간 이내 마감`

3. **상태 판정 5단계 우선순위:**
   ```text
   1. 취소공고 ➔ CANCELLED
   2. 데이터 충돌 ➔ DATA_CONFLICT
   3. 마감일 결측 ➔ HOLD_MISSING_DEADLINE ('마감일 공식 원문 확인 필요')
   4. 현재시각 < 마감시각 ➔ OPEN (잔여시간별 마감임박 배지)
   5. 현재시각 >= 마감시각 ➔ CLOSED
   ```

## 4. 승인 권한 및 통제 규칙 (Approval & Authority)

1. **승인 주체의 절대성:**
   - `APPROVED` 상태는 오직 **회장님**만이 부여할 수 있다.
   - AI 어시스턴트(Alex)와 개발자는 어떠한 경우에도 스스로 `APPROVED` 상태를 선언하거나 임의로 부여할 수 없다.
   - `STAGED` 상태가 되었다고 해서 `APPROVED`로 자동 전이되지 않는다.

2. **운영 배포(`main`) 잠금 원칙:**
   - 회장님의 명시적 승인(`APPROVED`) 없이 `main` 브랜치 병합 또는 운영 배포(`deploy:production`)를 시도하면 빌드/배포 스크립트가 즉시 에러를 발생시키고 실행을 중단한다.

3. **외부 알림 통제:**
   - 텔레그램, 카카오톡 알림 발송은 운영 배포와 별개의 독립 승인 대상이다.
   - 회장님의 명시적 "알림 발송 승인" 지시가 있기 전에는 테스트/운영 환경 모두에서 발송되지 않는다.
   - 기본 환경변수는 항상 `SEND_TELEGRAM=false`, `SEND_KAKAO=false`, `AUTO_PUBLISH=false`로 고정한다.

## 5. 4대 확정 업종 분류 기준

공개 화면 및 대외 표기는 반드시 다음 4대 분류 체계만을 사용한다.

1. **제작·시공:** 간판, 안내판, 표찰·현판, 현수막게시대, 전광판, 디지털사이니지, 조형물, 랩핑, 사인물 제작·설치
2. **인쇄·출판:** 책자, 보고서, 포스터, 리플릿, 카탈로그, 시험지, 홍보물, 편집디자인 및 인쇄
3. **출력·인쇄 장비:** 디지털 인쇄기, 잉크젯 프린터, 대형 출력기, 플로터, 커팅기, 코팅기, 후가공 장비
4. **출력소재·잉크:** 잉크, 토너, 출력용 필름, 시트지, 현수막 원단, 인쇄용지, 코팅필름, 출력 관련 소모재

## 6. Git 브랜치 관리 및 Push 절대 통제 규칙 (Force Push 금지)

1. **`git push --force` 절대 금지:**
   - 모든 원격 브랜치(`main`, `staging`, 작업 브랜치 포함)에 대한 `git push --force` 실행을 엄격히 금지한다.
   - `git push --force-with-lease` 역시 회장님의 사전 명시적 승인 없이 절대 실행하지 않는다.
2. **이력 재작성(History Rewriting) 금지:**
   - `main` 및 `staging` 브랜치에 이미 푸시된 커밋 이력을 재작성(`rebase -i`, `commit --amend`)하지 않는다.
   - 수정 및 보완이 필요한 경우 항상 **새로운 일반 커밋(Forward-only Commit)**을 생성하여 푸시한다.
3. **강제 푸시 판단 시 보고 의무:**
   - 만약 브랜치 꼬임 등으로 강제 푸시가 불가피하다고 판단될 경우, 이를 독단적으로 실행하지 않고 반드시 그 사유와 복구 계획을 회장님께 먼저 보고한 후 승인을 받는다.
