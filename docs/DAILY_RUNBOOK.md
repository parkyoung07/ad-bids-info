# SignBid 일일 운영 표준 런북 (DAILY_RUNBOOK)

## 1. 개요
본 문서는 매일 진행되는 SignBid 공고 수집, 검증, 마감시한 판정, Staging 반영, 회장님 보고 및 운영 배포 15단계 표준 프로세스를 정의한다.
AI 어시스턴트 및 운영자는 임의로 순서를 변경하거나 단계를 생략할 수 없다.

---

## 2. 15단계 일일 운영 프로세스

```
 1. 운영 공고 읽기 ──> 2. 마감/취소 갱신 ──> 3. 최근 3일 API 수집 ──> 4. 복합키 중복 제거
         │
         ▼
 5. 부적합/격리 제외 ──> 6. 순신규 후보 산출 ──> 7. 4대 업종 분류 ──> 8. 원문 대조표 작성
         │
         ▼
 9. Staging 반영 ──> 10. 모바일/PC 점검 ──> 11. 회장님 보고 ──> 12. 작업 중지 및 승인 대기
         │
         ▼ (회장님 승인 시)
 13. 운영 배포 ──> 14. 실서버 재검증 ──> 15. 외부 알림 발송 (별도 승인 시)
```

### [1단계] 운영 공고 현황 읽기 (Read Current Production)
- `public/data/bids.json` (운영 데이터)의 전체 공고 수, 진행 건수, 마감 건수를 확인한다.

### [2단계] 마감·취소·정정 상태 갱신 (Sync Status)
- 현재 시각 기준 투찰마감일시(`bidClseDt`)가 경과한 공고는 `CLOSED`(마감)으로 즉시 상태를 갱신한다 (KST 시·분·초 기준).

### [3단계] 최근 3일 공식 API 공고 수집 (Fetch Recent Bids)
- 조달청 나라장터 공식 OpenAPI(용역·물품·공사)를 통해 최근 3일간 등록·수정된 공고를 수집한다.

### [4단계] 기존 운영 공고와 복합키로 중복 제거 (De-duplicate by Composite Key)
- 고유 식별키는 반드시 복합키(`bidNtceNo + "-" + bidNtceOrd`)를 사용한다.
- 기존 운영 DB에 이미 존재하는 복합키는 신규 수집 목록에서 원천 배제한다.

### [5단계] 마감·취소·구차수·오분류 제외 및 격리 (Filter & Isolate)
- 마감된 공고, 취소공고, 구차수(이전 차수), 교육/연구/기계/순수전기공사 등 무관 공고를 필터링한다.
- 데이터 충돌 이력이 있는 공고(`R26BK01733924` 등)는 `DATA_CONFLICT`로 격리한다.
- 공식 마감일시가 없는 공고는 `HOLD_MISSING_DEADLINE`으로 별도 보류한다.

### [6단계] 순신규 후보 산출 및 마감 임박 판정 (Calculate Net New Candidates & Urgency)
- **산출 공식:**
  $$\text{순신규 후보} = \text{오늘 수집 결과} - \text{기존 운영 복합키} - \text{마감} - \text{취소} - \text{구차수} - \text{마감일 결측(HOLD)} - \text{충돌(CONFLICT)} - \text{오분류}$$
- 남은 마감시각에 따라 4단계 마감 배지를 부여한다:
  - 24시간 초과: `자동수집 후보`
  - 24시간 이하: `마감 임박`
  - 3시간 이하: `긴급 · 마감 임박`
  - 1시간 이하: `긴급 · 1시간 이내 마감`

### [7단계] 4대 업종으로 분류 (Classify into 4 Standard Categories)
- 순신규 후보를 확정된 4대 업종(제작·시공, 인쇄·출판, 출력·인쇄 장비, 출력소재·잉크)으로 정밀 분류한다.

### [8단계] 공고별 원문 데이터 표 작성 (Build Verification Table)
- 공고번호-차수, 공식 공고명, 발주기관, 배정예산, 마감일시(시·분·초), 잔여시간, 공식 상세 URL을 원문 그대로 표로 정리한다.

### [9단계] Staging에만 반영 (Deploy to Staging Only)
- 신규 후보 공고 및 블로그 초안(`draft: true`)을 Staging 브랜치/환경에 반영한다.

### [10단계] 모바일·PC 화면 점검 (Cross-Device Inspection)
- Staging 화면에서 모바일(터치, 1단 뷰) 및 PC(그리드, 링크 직통) 표시 상태를 점검한다.

### [11단계] 회장님께 보고 (Report to Chairman)
- [A. 순신규 후보 공고 목록 (원문 대조표)] + [B. 시스템 무결성 점검 결과] + [C. Staging 검증 URL 및 커밋 SHA]를 명확한 증거와 함께 보고한다.

### [12단계] 작업 중지 및 승인 대기 (STOP & Await Approval)
- 보고 완료 후 추가 작업을 자의적으로 진행하지 않고 즉시 작업을 멈추고 회장님의 명시적 승인을 기다린다.

### [13단계] 승인받은 경우에만 운영 배포 (Deploy Production on Approval)
- 회장님의 명시적 승인(`APPROVED`)을 득한 경우에 한하여 `npm run deploy:production`을 실행한다.

### [14단계] 운영 배포 후 실서버 재검증 (Post-Deploy Verification)
- 운영 배포 후 실서버 URL에서 데이터 건수, 링크 유효성, HTTP 응답 상태를 최종 확인한다.

### [15단계] 별도 승인을 받은 경우에만 외부 알림 발송 (Send Alerts on Explicit Approval)
- 회장님께서 "알림 발송 승인"을 명시하신 경우에만 `npm run notify:approved`를 통해 텔레그램/카카오톡을 발송한다.
